# Plano: Melhorias no dev.md (12 tasks)

## Objetivo

Implementar 12 tasks (8 issues: 4 críticos + 8 importantes/sugestões) identificadas
por code-review comparativo do `dev.md` com padrões de mercado 2025-2026 e o
`task-build.md` (recentemente melhorado).

O `dev.md` atual tem 154 linhas e é funcional mas genérico — falta profundidade
em áreas que pesquisas recentes mostram serem críticas para agentes de implementação.

## Pesquisa de Referência (resumo)

Pesquisa realizada em 7 fontes primárias sobre prompting de coding agents (2025-2026):

1. **SurePrompts** (abr 2026): 6 skills universais — spec-writing, scope, context,
   acceptance criteria, tool constraint, critical review
2. **SuperPrompts** (jun 2026): Role-scoped context, deterministic output constraints,
   tool-aware structuring; "cost of bad prompt is exponential with steps"
3. **Agents UI** (fev 2026): Scope-first prompts, incremental decomposition,
   verification steps, constraint-based prompts
4. **Agentbrisk** (abr 2026): CLAUDE.md structure, context priming, few-shot examples
5. **AgentsCamp** (mai 2026): Chaining, few-shot, context management, tool-use patterns
6. **Laxaar** (ago 2026): 4 prompt patterns — decompose, constrain, cite-the-file,
   stop-condition; "stop-condition prevents agent from 'helpfully' touching extra files"
7. **Ready Solutions** (abr 2026): Subagent orchestration — parallel fan-out,
   sequential review chains, hierarchical planner-executor
8. **ACL 2026 / arXiv** (2026): Self-repair via structured reflection, 2 rounds
   capture 76-95% of gains; validator should return location + observed + alternatives

- [ ] **C2. Stop Conditions explícitas**

  **Seção**: Nova subseção "Stop Conditions" na seção "Regras" (após "Qualidade")

  **Mudança**: Definir quando o dev PARE e quando NÃO PARE:

  **PARAR quando:**
  - Todos os arquivos do plano foram modificados
  - Todos os testes passam
  - Build/lint não retornam erros
  - Acceptance criteria do plano foram atendidos

  **NÃO PARAR (continuar) quando:**
  - Há erros de build/lint/test não resolvidos
  - Arquivos do plano ainda não foram tocados
  - Acceptance criteria não foram verificados

  **NÃO FAZER (proibições de escopo):**
  - Refatorar código fora do escopo da task
  - Adicionar features não solicitadas
  - Modificar testes existentes (exceto para tornar compatíveis com mudanças)
  - Instalar dependências novas sem autorização
  - Atualizar README ou docs não relacionados

  **Motivação**: "An agent without a stop condition will keep going. It will
  'improve' the code, add 'defensive' checks, rename variables for 'clarity,' and
  touch files that have nothing to do with the task." (SurePrompts 2026)

  **Acceptance**: Subseção existe; 3 categorias (PARAR/NÃO PARAR/NÃO FAZER) documentadas;
  pelo menos 4 items em cada categoria

  **Verify**:
    - Run: `grep -n "Stop Condition\|PARAR quando\|NÃO FAZER\|Refatorar código fora" .config/opencode/agents/dev.md`
    - Expected: deve retornar a subseção com categorias

  **Files**: `.config/opencode/agents/dev.md`
  **Complexidade**: média

- [ ] **C4. Auto-verificação guiada com iteração controlada**

  **Seção**: Refinar Step 7 "Verificação interna" — adicionar padrão de iteração

  **Mudança**: Expandir o step 7 com padrão de self-repair estruturado:

  1. **Rodar verificação** (build/lint/test conforme stack detectada)
  2. **Se PASSAR** → marcar ✅ e avançar
  3. **Se FALHAR** → categorizar o erro:
     - **Sintaxe/tipo**: corrigir diretamente (taxa de sucesso ~77%)
     - **Lógica/assertion**: investigar causa raiz antes de corrigir (taxa ~45%)
     - **Dependência/config**: verificar imports e config antes de corrigir
  4. **Aplicar correção** — UMA mudança por iteração (não múltiplas)
  5. **Re-verificar** — rodar o mesmo comando
  6. **Se 2ª iteração falhar** → ESCALAR via QUESTION TOOL (não 3 iterações)
     - Header: `"Verificação falhou após 2 tentativas"`
     - Opções: "Corrigir manualmente" / "Pular verificação" / "Parar"

  **Motivação**: "Two repair rounds capture the majority (76-95%) of achievable gains.
  Assertion errors are the hardest to repair at ~45%." (arXiv 2604.10508, 2026).
  Reduzir de 3 para 2 iterações e categorizar erros melhora eficiência.

  **Acceptance**: Step 7 descreve 3 categorias de erro; iteração limitada a 2 rounds
  (não 3); cada iteração faz UMA mudança; QUESTION TOOL com 3 opções documentado

  **Verify**:
    - Run: `grep -n "categorizar\|Sintaxe\|Lógica\|2ª iteração\|2 tentativas" .config/opencode/agents/dev.md`
    - Expected: deve retornar categorias e limite de 2 iterações

  **Files**: `.config/opencode/agents/dev.md`

## Riscos

- **Expansão do tamanho**: dev.md vai de ~154 para ~250-280 linhas.
  Risco baixo — o task-build.md já tem 619 linhas e funciona bem.
  → Mitigação: manter seções concisas; usar tabelas em vez de parágrafos

- **Conflito com contratos do task-build**: task-build.md já define
  "Contratos de Output" para dev. Risco médio — pode haver duplicação.
  → Mitigação: dev.md define o FORMATO interno; task-build.md define
  o CONTRATO externo. Referenciar task-build para o contrato.

- **Muitas restrições podem paralisar o agente**: Over-constraining pode
  fazer o dev gastar mais tempo em compliance que em implementação.
  → Mitigação: restrições ordenadas por prioridade; "bom senso" como fallback

- **Timeouts podem ser inadequados para tasks grandes**: 5min/arquivo pode
  ser pouco para refatorações complexas.
  → Mitigação: timeout total (10min) é o guard rail; QUESTION TOOL se exceder
